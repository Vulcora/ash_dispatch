# 0.9.4 — the tenant through the whole flow

**Status: implemented in 0.9.4 (`release/0.9.4`); corrected in 0.9.4-rc.1 after
an independent review of rc.0.** Kept as written, as the record of what was
decided before any of it existed. Three things turned out differently in the
building, and they are marked **[built]** where they appear: `tenant_column:`
is on the receipt only (the other two bases have had the column since 0.9.0),
the work plan's 86 call sites were 87 — the `skip_if_read` notification read
was missed — and the tenant a receipt remembers is kept under a key of the
library's own rather than read out of Ash's internals. The upgrade-facing
version of this page is the
[Tenancy](../../lib/documentation/topics/tenancy.md) guide.

**What the review of rc.0 changed**, marked **[rc.1]** where it appears below:

- **The work plan's count was not the whole set.** Four reads of the *host's*
  resources were not on the list of 87 and were still untenanted:
  `lib/event/helpers.ex`'s `should_send_filter` query, `CounterLoader`'s
  audience check, `CounterHandler`'s `load_and_traverse_path/3` (which was
  given a `tenant` parameter nobody passed) and the context `CounterHandler`
  builds for a filter-based audience. All four fail closed behind a `rescue`,
  so a per-tenant host lost deliveries and counters silently. The count is now
  held by an AST walk over `lib/` rather than by a hand-kept list — 82
  data-layer call sites, every one of them taking its tenant from
  `AshDispatch.Tenancy`.
- **"The tenant" is two strings, and this page did not say so.** The `tenant`
  column is `Context.tenant_key/1`; the schema is `Ash.ToTenant`'s answer. rc.0
  used the column's string everywhere it serialised a tenant, so for a host
  whose tenants are structs every send was cancelled and no tenant was ever
  scrubbed. Everything that becomes a schema name goes through
  `AshDispatch.Tenancy.prefix/2` now; the column is unchanged and making it
  hold the schema name is 0.10.0 (BACKLOG 11).
- **"Oban's `unique` keeps a slow tenant from being enqueued twice"** (§9
  below) was a reason given for the fan-out and was never built. It is built
  now, on the enqueue rather than on the worker, so the crontab entry job is
  untouched.
- **A missing table is not a missing schema.** §"what fails closed" treated
  `42P01` as unfixable. It is the normal state of a tenant between
  `create schema` and `mix ash.migrate`, so it is retried; only `3F000` is
  cancelled.
- **`:tenants` guards three outside paths, not every `:tenant`.** The guide
  said more than that was true, and rc.0 trusted a webhook's route param
  without checking it at all. See the guide's table.

AshDispatch knows what a tenant is since 0.8.8 and stores one since 0.9.0, but
only ever as *a value it passes along*: `context.tenant` reaches the preference
checker, and `Context.tenant_key/1` writes a string onto an in-app
notification. Every read and write the library makes is made without a tenant.

For a host whose receipts and notifications live in the public schema that is
fine, and it must stay fine. For a host with `multitenancy strategy :context`
and one Postgres schema per tenant it is not: a receipt written during a
tenant's action lands in `public.delivery_receipts`, the send worker reads it
back from `public` by luck rather than by design, and `ScrubSensitiveContent`
— which runs a raw `UPDATE` against a table name with no prefix — never
touches a tenant schema at all.

0.9.4 carries the tenant through the whole flow, for the hosts that ask for it,
and changes nothing for everyone else.

## The rule this has to obey

A 0.9.x patch never requires a migration and never changes a default. Nothing
below arrives until the host switches it on:

| Switch | Where | Effect |
|---|---|---|
| `multitenancy: :context` | `DeliveryReceipt.Base`, `Notification.Base`, `Preference.Base` | the resource gets an Ash `multitenancy` block; the host generates its own migration |
| `tenant_column: true` | `DeliveryReceipt.Base` **[built]** | a nullable `tenant` column on a resource that stays in the public schema. Only the receipt needs it: the other two bases have had the column since 0.9.0 |
| `job_args: :minimal` | `config :ash_dispatch` | the email job carries ids, not bodies |
| `tenants: {M, :f, []}` | `config :ash_dispatch` | the cron workers run once per tenant |

Everything else is threading a value that is `nil` today and stays `nil` for a
host that passes none.

### Why "does nothing" really means nothing changes

One helper decides whether a tenant is ever mentioned to Ash:

```elixir
defmodule AshDispatch.Tenancy do
  @doc "`[tenant: t]` when the resource is multitenant and `t` is not nil; `[]` otherwise."
  def opts(resource, tenant)
end
```

Every read and write in the library goes through it (`Ash.get(resource, id,
[authorize?: false] ++ Tenancy.opts(resource, tenant))`). For a resource
without a `multitenancy` block — which is what every consumer has today — it
returns `[]`, so the call is byte-for-byte the call made now. This is the whole
of the compatibility story, and it is one function, so it can be tested once
rather than argued about per call site.

It must be `Ash.Resource.Info.multitenancy_strategy/1` that decides, not "is
the tenant nil": a host that passes `tenant:` to a non-multitenant resource is
relying on Ash to ignore it, and a library should not rely on that.

## The flow, step by step

### 1. Dispatch

`context.tenant` already exists and is already filled on both paths:
`Dispatcher.dispatch/4`'s `:tenant` option (lib/dispatcher.ex:194) and the
action's tenant for an action-triggered event
(lib/notifier/dispatch_handler.ex:148). Nothing to add.

What is missing is the *loads*: `apply_channel_load/2` (lib/dispatcher.ex:2021)
and the notifier's `maybe_load_relationships/3`
(lib/notifier/dispatch_handler.ex:243) call `Ash.load/3` on the host's own
record without a tenant. For a schema-per-tenant resource that fails, or worse,
loads from the wrong schema.

### 2. Recipient resolution

`AshDispatch.RecipientResolver.Resolver` queries the user resource
(lib/recipient_resolver/resolver.ex:412), as does the legacy audience path
(lib/event/helpers.ex:417) and `Calculations.LoadUser`
(lib/calculations/load_user.ex:18, :59). If the host's users are per tenant,
every audience resolves to nobody today.

The resolver's `resolve/3` already receives the context, so the tenant is in
hand; it has to reach the query.

### 3. The receipt

`create_receipt/4` (lib/dispatcher.ex:857) writes the receipt. With
`multitenancy: :context` the write needs the tenant, and that is the point at
which a dispatch without one must fail loudly:

> `AshDispatch: this dispatch has no tenant, and MyApp.Deliveries.DeliveryReceipt
> is per tenant. Pass `tenant:` to `Dispatcher.dispatch/4`, or run the action
> with a tenant.`

Not a fallback to the public schema: two homes for receipts is how a receipt
stops being an audit trail.

Hosts that have both tenant-scoped and system-wide events should keep receipts
public and use `tenant_column: true` (below) instead; `multitenancy: {:context,
global?: true}` is available for the same reason but every read then has to be
sure which schema it means, which is exactly the ambiguity this design is
removing.

### 4. The Oban job args

The job is the tenant's exit from the process. Every send worker reads the
receipt back by id alone:

- `Workers.SendEmail.perform/1` — lib/workers/send_email.ex:142
- `Workers.SendSMS.perform/1` — lib/workers/send_sms.ex:50
- `Workers.SendWebhook.perform/1` — lib/workers/send_webhook.ex:115

So the args gain `"tenant"` (the string from `Context.tenant_key/1`), written
by `Transports.Email.job_args/3` (lib/transports/email.ex:149) and by the SMS,
webhook, Slack and Discord transports where they build theirs. A job enqueued
before the upgrade carries no `"tenant"` key, reads as `nil`, and behaves as it
does today — which is what makes this safe to deploy while jobs are in flight.

### 5. `job_args: :minimal`

`oban_jobs` is **not** per tenant. It is one table in the public schema, which
means that today, for a host with per-tenant receipts, the one place a tenant's
rendered message bodies would leave their schema is the job args
(`full_job_args/3`, lib/transports/email.ex:187: `subject`, `html_body`,
`text_body`).

0.8.7 already solved this for sensitive events: the args carry only
`receipt_id`, `event_id` and `attachments`, and the worker reads the envelope
from the receipt. `job_args: :minimal` makes that the shape for every event:

```elixir
config :ash_dispatch, job_args: :minimal
```

- Default `:full` — today's behaviour, for everyone.
- **Default `:minimal` when the receipt resource is per tenant**, because there
  the alternative is a tenant's letter in a public table. That is a new default
  for a host that has just switched receipts to per-tenant schemas, which is an
  opt-in, so the rule holds.
- `attachments` stay in the args either way, as they do for sensitive events
  today: they exist nowhere else, a retry reads them back from the original
  job, and no scrub reaches them.

The cost is one extra receipt read per send on the first attempt. Every retry
already pays it (`new_for_receipt/1`).

### 6. Send

Inside the worker, everything the send touches needs the tenant it took out of
the args:

- the receipt itself: `ReceiptStatus` (lib/receipt_status.ex:60, 84, 90, 115,
  139, 153, 181, 215) — eight updates, all without a tenant
- `Delivery.hold/2` → `ReceiptStatus.skip/2` (lib/delivery.ex:92)
- the in-app notification: `insert_notification/3`
  (lib/transports/in_app.ex:443), `find_by_idempotency_key/2`
  (lib/transports/in_app.ex:470), and the retry path
  (lib/transports/in_app.ex:161)
- the `skip_if_read` notification lookup (lib/workers/send_email.ex:517)
- the re-reads each transport does after enqueueing: email
  (lib/transports/email.ex:281), SMS (lib/transports/sms.ex:117), webhook
  (lib/transports/webhook.ex:307)

The honest way to thread this is not twenty keyword lists. `ReceiptStatus`
already has the receipt, and a receipt loaded with a tenant carries it in
`__metadata__`; `Ash.Changeset.for_update/3` on a record keeps it. The
implementation should therefore:

1. load the receipt **once**, with the tenant, at the top of each worker;
2. let every later update derive the tenant from the struct it was handed
   (`Ash.Resource.put_metadata`/`Ash.Changeset.set_tenant` from
   `receipt.__metadata__.tenant`), through one private helper in
   `ReceiptStatus`;
3. pass a tenant explicitly only where there is no loaded struct to carry one —
   the notification create, the idempotency read, the cron queries.

That keeps the call sites readable and makes "the tenant came from the receipt
we are updating" true by construction rather than by discipline.

### 7. The receipt's own `tenant` column

For a host that keeps receipts in the public schema and wants per-tenant
reports — BACKLOG 10 names this: *"the receipt carries `actor_id` but no
`tenant`; per-tenant receipt reports read it through the source record for
now"* — `tenant_column: true` adds:

```elixir
attribute :tenant, :string, allow_nil?: true, public?: true
```

filled from `Context.tenant_key/1` at creation, exactly as
`Notification.Base`'s `tenant` is today. Nullable, so existing rows need no
backfill; absent unless switched on, so no migration for anyone else. The
dispatcher already passes unknown attributes through `skip_unknown_inputs:`
(lib/dispatcher.ex:853), which is how `actor_id` landed in 0.9.0 without
breaking hand-rolled receipt resources — `:tenant` joins that list.

The two are not exclusive: a per-tenant receipt may also carry the column, and
a report that spans tenants then has something to group by without reading
twenty schemas.

### 8. Provider webhooks

This is the hard one, and it is hard for a reason that is not ours: a provider
webhook arrives with a message id and nothing else.
`WebhookHandlers.Resend.process_webhook/1` looks the receipt up by
`provider_id` (lib/webhook_handlers/resend.ex:187) and then updates it
(lib/webhook_handlers/resend.ex:235). With receipts per tenant, there is no
tenant in the request, and the lookup searches the wrong schema.

Three answers, in the order to prefer them:

1. **A per-tenant webhook endpoint.** The host's router already knows how to
   put a tenant in a path: `POST /webhooks/resend/:tenant`. `process_webhook/2`
   takes `tenant:` and the lookup is scoped. Nothing depends on what the
   provider echoes back, so it works for every provider. This is the
   recommended setup and the one the guide should show.
2. **A provider tag.** When the dispatch has a tenant, the email transport adds
   it to the outgoing message as a tag or header (`X-AshDispatch-Tenant`), and
   `process_webhook/2` reads it out of the payload when it is there. Cheap for
   Resend, which echoes both; not available from every provider, and a tag is a
   recipient-visible header, so it must be opt-in
   (`webhook_tenant_tag: true`) and must never carry anything but the tenant
   key.
3. **Keep receipts public** and use `tenant_column: true`. Provider webhooks
   then work unchanged, which for a host whose only reason to go per-tenant was
   data residency may be the right trade.

What the implementation must **not** do is fan the lookup out across every
tenant schema until it finds the row. It turns one indexed read into N, and a
webhook endpoint is the one place in the library an outsider can trigger work.

### 9. The cron workers

Both scheduled workers read across all receipts:

- `RetryFailedDeliveries`: the failed query (lib/workers/retry_failed_deliveries.ex:137),
  the stranded sweep (lib/workers/retry_failed_deliveries.ex:196), and three
  updates (lib/workers/retry_failed_deliveries.ex:289, 381, 402)
- `ScrubSensitiveContent`: a raw `Config.repo().update_all/2` against the
  table name (lib/workers/scrub_sensitive_content.ex:78, query built at
  lib/workers/scrub_sensitive_content.ex:107) — **no prefix at all**, so it
  silently scrubs nothing in a tenant schema. A sensitive body in a tenant
  schema lives forever today.

Per-tenant receipts therefore need the host to say what the tenants are:

```elixir
config :ash_dispatch, tenants: {MyApp.Tenants, :all_keys, []}
```

The cron job then fans out: the scheduled job reads the list and enqueues one
job per tenant (`%{"tenant" => key}`), rather than looping inline. Reasons: one
tenant's failure does not stop the next one's, the work spreads over the queue
instead of one long-running job, and Oban's `unique` keeps a slow tenant from
being enqueued twice. **[rc.1]** The `unique` was not built in rc.0 and is now,
declared on the enqueue rather than on either worker — `Oban.Plugins.Cron`
inserts the crontab entry job itself, and a `unique` on the worker would apply
to that insert too. The entry job stays the one in the crontab, so the
installer's cron configuration does not change.

Without `tenants:` configured and with per-tenant receipts, the workers should
log an error once per run and do nothing — not fall back to the public schema,
where they would find nothing and report success.

`ScrubSensitiveContent` also needs `prefix:` on its `update_all`, which is a
one-line change once the tenant is known.

### 10. Preview

`AshDispatch.Preview` reads the record a preview is rendered from
(lib/preview.ex:533, :537) and so do the manual-trigger helpers
(lib/resources/manual_trigger/helpers.ex:589, :640, :742, :779) and the user
lookup behind a manual trigger (lib/resources/manual_trigger.ex:360). A preview
of a tenant's record needs `tenant:` in `Preview.render/3`'s options and in the
ManualTrigger actions' arguments — the actions have a tenant of their own
already (lib/resources/manual_trigger.ex:233), it simply never reaches the
read.

A preview must stay side-effect free: the tenant is a read option, nothing
more.

### 11. Preferences, notifications, counters

- `UserPreference.Resource` filters on the `tenant` **column** today
  (lib/user_preference/resource.ex:46, 80) and its reads
  (lib/user_preference/resource.ex:282, 315, 332) and writes
  (lib/user_preference/resource.ex:242, 247, 265) have no Ash tenant. With
  `Preference.Base` per tenant the column becomes redundant — but it must keep
  working, because the column is what a host on public preferences uses. Both
  meanings have to be read from one place, and the decision has to be the
  resource's `multitenancy_strategy`, not a second config key.
- `NotificationLoader` reads (lib/helpers/notification_loader.ex:68, 140, 144)
  and `Notification.Base`'s `mark_all_as_read` bulk update
  (lib/resources/notification/base.ex:92) and `:unread_count`
  (lib/resources/notification/base.ex:279).
- `AshDispatch.Phoenix.LiveView`'s `:tenant` option
  (lib/phoenix/live_view.ex:152, 190) means "filter by column" today and would
  mean "the Ash tenant" for a per-tenant notification resource. One option, two
  meanings, resolved by the resource — and documented in one paragraph, because
  a host reading the guide will otherwise assume the wrong one.
- Counters: `CounterLoader` (lib/helpers/counter_loader.ex:183, 297, 364) and
  `CounterHandler` (lib/notifier/counter_handler.ex:104, 174) count the host's
  own resources. If those are per tenant, every counter is 0 today.

### 12. The gate and the eligibility check (0.9.3)

`AshDispatch.Gate.Info` carries `:tenant` at dispatch and `nil` at send
(lib/gate.ex:155), and `EligibleRecipient`'s send-stage opts likewise
(lib/eligible_recipient.ex:147, `send_verdict/1`). Once the job args carry the
tenant, both should carry it at the send stage too — a host's gate that reads
its own database needs it, and the two stages otherwise disagree about what
they know.

## Estimate

| Piece | Size | Notes |
|---|---|---|
| `AshDispatch.Tenancy` + its tests | S | one function; the whole compatibility story rests on it |
| `multitenancy:` / `tenant_column:` in the three Base macros | M | plus a test that a resource without them generates byte-identical DSL |
| Thread the tenant: dispatch → receipt → job args → worker → receipt | M | ~50 of the call sites, mechanical once the helper exists |
| `ReceiptStatus` taking the tenant from the struct | S | one private helper; it is what turns 32 transport call sites into a handful |
| `job_args: :minimal` | S | `full_job_args/3` already has a minimal sibling for sensitive events |
| Recipient resolution, counters, notification loader, preview | M | the host's own resources; needs fixtures that are actually per tenant |
| Cron fan-out + `tenants:` + the scrub's `prefix:` | M | the scrub is a one-liner; the fan-out needs its own worker and tests |
| Provider webhooks | M | `process_webhook/2`, the optional tag, and a guide section that is honest about the trade |
| Guide: *Tenancy* | S–M | one page, and the two meanings of `:tenant` spelled out |

**Roughly a release's worth of work: two to three days of focused
implementation, and the test fixtures are the slow half.** The library's test
suite has no per-tenant resource at all today, so the first task is an ETS or
Postgres fixture with `strategy :context` — without it every "the tenant
reached the read" test is a test of a keyword list.

The one piece that cannot be finished inside 0.9.x is the choice of a *default*
for `job_args`: `:minimal` is the better default for everyone (a rendered body
in `oban_jobs` is a copy nobody scrubs), but making it the default for hosts on
public receipts changes behaviour and belongs in 0.10.0.
